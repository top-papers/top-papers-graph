# Capacity-150: пошаговое заполнение enrichment-форм

Это руководство объясняет простым языком, как подготовить три файла для следующего этапа
VLM A/B-эксперимента.

Используйте только актуальный workspace:

```text
runs/vlm_ab/qwen3vl-cap150-remediation-working-v1/capacity_enrichment_handoff_v5
```

Workspace `v5` имеет write-once статус. Не изменяйте его файлы и не сохраняйте внутрь него
результаты заполнения. Предыдущие версии `v3` и `v4` оставлены только как история.

SHA256 файла `capacity_enrichment_handoff_v5/handoff_manifest.json`:

```text
2fe9d274d662ce097b7ea8af4113684b9bb1b9328b38f4e662f7dd14c6213830
```

## Перед началом

- Не угадывайте значения и не заполняйте поля формально.
- Машинные подсказки в формах не являются проверкой фактов, identity или лицензии.
- Формы работают локально и не выполняют сетевых запросов.
- Черновик автоматически сохраняется в локальном хранилище браузера.
- Дополнительно экспортируйте draft JSON, если работа занимает несколько дней.
- После перезагрузки страницы локальные evidence-файлы и финальные binding-файлы нужно
  выбрать заново.
- Финальные JSON-файлы храните в отдельной рабочей папке вне
  `capacity_enrichment_handoff_v5`.

Перед работой понадобятся:

- точные revisions репозиториев модели и обучающих датасетов;
- локальные копии файлов обучения для вычисления SHA256;
- список всех идентификаторов, покрытых обучением;
- надёжные evidence-файлы для проверки identity 15 статей;
- исходные статьи и изображения для 150 групп;
- подтверждённые лицензии изображений.

Если каких-либо сведений нет, остановитесь и запросите их у владельца данных. Не заменяйте
отсутствующие сведения предположениями.

## Шаг 1. Training lineage

Откройте файл:

```text
capacity_enrichment_handoff_v5/training_lineage_form.html
```

Эта форма описывает точные данные, на которых обучалась модель.

### 1.1. Источники обучения

Для каждого репозитория модели или датасета заполните следующие поля.

| Поле | Что указать |
| --- | --- |
| `repo_id` | ID репозитория, например `organization/dataset` |
| `repo_type` | `Модель` или `Датасет` |
| `revision` | Точный Git commit из 40 строчных hex-символов; не `main` и не название ветки |
| `path` | Путь файла внутри закреплённого репозитория |
| `SHA256` | SHA256 точного файла; лучше вычислить кнопкой выбора локального файла |
| `row_count` | Точное неотрицательное количество записей |

Кнопка **«Добавить файл»** добавляет ещё один файл того же репозитория. Кнопка
**«Добавить источник обучения»** добавляет другую модель или другой датасет.

Значение `row_count=0` используйте только для файла, который действительно не представляет
строки данных. Не используйте ноль вместо неизвестного значения.

### 1.2. Покрытие

Форма показывает пять флажков:

- ID статей;
- исходные документы;
- группы создателей;
- байты изображений;
- промпты.

Ставьте флажок только тогда, когда соответствующий список ниже полностью описывает обучение.
Финальный экспорт требует честного подтверждения всех пяти пунктов. Если подтвердить какой-либо
пункт нельзя, сначала соберите недостающие данные.

### 1.3. Покрытые идентификаторы

Указывайте по одному непустому значению на строку.

| Поле | Содержимое |
| --- | --- |
| `paper_ids` | Canonical ID всех обучающих статей |
| `source_document_ids` | ID всех исходных обучающих документов |
| `creator_group_ids` | ID всех групп создателей |
| `image_sha256s` | SHA256 всех обучающих изображений |
| `prompt_sha256s` | SHA256 всех обучающих промптов |

Примеры допустимых canonical paper ID:

```text
doi:10.1234/example
arxiv:2501.05547
paper:internal-example
```

Canonical paper ID должен быть записан строчными буквами. Все значения внутри каждого списка
должны быть уникальными. Каждый SHA256 должен содержать 64 строчных hex-символа.

### 1.4. Экспорт lineage

1. Нажмите **«Проверить и экспортировать training_lineage_manifest.json»**.
2. Исправьте все ошибки, которые покажет форма.
3. Дождитесь завершения вычисления SHA256, если оно ещё выполняется.
4. Получите финальный файл `training_lineage_manifest.json`.
5. Не редактируйте экспортированный JSON вручную.

Кнопка **«Экспортировать черновик envelope»** создаёт только резервный черновик
`training_lineage_manifest_draft.json`. Он не заменяет финальный manifest.

### 1.5. Неизменяемый URL

Source form потребует HTTP(S)-адрес финального `training_lineage_manifest.json`, закреплённый на
конкретном commit или другой неизменяемой revision.

Пример:

```text
https://raw.githubusercontent.com/org/repo/0123456789abcdef0123456789abcdef01234567/training_lineage_manifest.json
```

URL не должен содержать credentials, query-параметры или fragment. В пути URL должна
присутствовать revision из 40–64 hex-символов. Если такого URL пока нет, опубликуйте manifest в
подходящем репозитории или передайте его владельцу pipeline для публикации.

## Шаг 2. Разрешение identity статей

Откройте файл:

```text
capacity_enrichment_handoff_v5/identity_resolution_form.html
```

Форма содержит 15 identity actions. Для каждого действия нужно определить правильный canonical
paper ID и приложить evidence.

### 2.1. Проверка статьи

1. Прочитайте текущий ID, машинного кандидата и машинное объяснение.
2. Найдите надёжный первичный источник: официальный landing page, DOI, arXiv или metadata record.
3. Сверьте название, авторов, год и содержание статьи.
4. Не принимайте машинного кандидата без независимой проверки.

### 2.2. Выбор решения

| Решение | Когда использовать | Что записать в resolved ID |
| --- | --- | --- |
| **Подтвердить текущий ID** | Текущий ID независимо проверен и верен | Точный текущий ID |
| **Заменить машинным кандидатом** | Машинный кандидат независимо проверен и верен | Точный показанный кандидат |
| **Заменить другим ID** | Верный ID найден вручную | Другой проверенный canonical ID |
| **Не разрешено** | Правильный ID пока неизвестен | Допустимо только в черновике |

Состояние **«Не разрешено»** блокирует финальный экспорт. Для строк с пустым текущим ID нужно
найти проверенный ID и выбрать замену.

### 2.3. Evidence

Для каждого identity action заполните:

| Поле | Что указать |
| --- | --- |
| `URL evidence` | Чистый HTTP(S) URL первичного источника без credentials, `?query` и `#fragment` |
| `SHA256 evidence` | SHA256 точного локального evidence-файла |
| Время получения | ISO timestamp, например `2026-07-23T12:00:00Z` |
| Примечания | Краткое объяснение, почему evidence подтверждает выбранный ID |

Для SHA256 используйте кнопку выбора локального evidence-файла. Evidence-файлом может быть
сохранённый PDF, metadata JSON или другой точный документ, соответствующий указанному URL.

### 2.4. Изменение ID и capacity plan

Если resolved ID совпадает с текущим ID, флажок **«Capacity plan регенерирован»** должен быть
выключен.

Если resolved ID изменился:

1. Экспортируйте identity draft.
2. Передайте draft владельцу pipeline.
3. Дождитесь фактической регенерации затронутого capacity plan.
4. Только после этого включите флажок **«Capacity plan регенерирован»**.

Не включайте этот флажок только для прохождения проверки формы.

### 2.5. Экспорт identity

1. Заполните все 15 actions.
2. Используйте кнопку **«Первая незаполненная»** для поиска оставшихся ошибок.
3. Нажмите **«Проверить и экспортировать identity submission»**.
4. Исправьте все показанные ошибки.
5. Получите `identity_resolution_submission.json`.

Файл `capacity_identity_resolution_draft.json` является только черновиком и не заменяет
финальный submission.

## Шаг 3. Заполнение 150 source groups

Откройте файл:

```text
capacity_enrichment_handoff_v5/source_submission_form.html
```

### 3.1. Глобальные привязки

В верхней части формы:

1. Выберите финальный `training_lineage_manifest.json`.
2. Вставьте его неизменяемый HTTP(S) URL.
3. Укажите время получения manifest в формате ISO timestamp.
4. Выберите финальный `identity_resolution_submission.json`.

Форма вычислит SHA256 обоих файлов и будет хранить их только в памяти вкладки. После
перезагрузки страницы или импорта черновика выберите оба файла заново.

### 3.2. Навигация

В форме находятся ровно 150 групп. Используйте:

- поиск по строке, ID или group ID;
- фильтр незаполненных групп;
- фильтр identity actions;
- фильтр машинных source probes;
- кнопку **«Первая незаполненная»**.

Индикатор прогресса показывает количество групп без построчных ошибок. Финальная проверка также
выполняет глобальные проверки уникальности и пересечений.

### 3.3. Основные поля группы

Для каждой группы выберите ровно одну primary task и заполните следующие поля.

| Поле | Что требуется |
| --- | --- |
| `sample_id` | Уникальный ID примера, например `capacity-001` |
| `canonical_paper_id` | Проверенный canonical ID статьи |
| `stratum` | `multimodal_hard`, `temporal_hard` или `easy_control` |
| `source_document_id` | Стабильный ID исходного документа |
| `creator_group_id` | Стабильный ID группы создателей |
| `model_task_prompt` | Полный вопрос, который получит модель |
| System instruction | Необязательно |
| Scientific grounding | Почему вопрос научно корректен и подтверждается источником |
| Notes | Необязательно |

При выборе primary task форма может установить `stratum`. Не меняйте его на несовместимое
значение.

Для строк с identity action поле `canonical_paper_id` должно точно совпадать с resolved ID из
импортированного `identity_resolution_submission.json`.

`sample_id` и `canonical_paper_id` должны быть уникальными среди 150 групп. Evaluation ID и
другие идентификаторы не должны пересекаться с training lineage.

### 3.4. Evidence статьи

Article evidence обязательно для каждой группы:

| Поле | Что указать |
| --- | --- |
| URL источника | Чистый HTTP(S) URL статьи или документа |
| SHA256 содержимого | SHA256 точного локального evidence-файла |
| `retrieved_at` | Время получения файла |

Metadata evidence необязательно. Но если заполнено хотя бы одно его поле, заполните все три:
URL, SHA256 и `retrieved_at`.

### 3.5. Изображения

Для каждой группы требуется минимум одно изображение. Для каждого изображения заполните:

| Поле | Что указать |
| --- | --- |
| `image_path` | Уникальный ASCII-путь внутри `assets/images/`, например `assets/images/group-001/figure-1.png` |
| SHA256 | SHA256 точных байтов изображения |
| Страница | Номер страницы источника |
| Локатор | Например `Figure 2`, `Panel B` или точное описание места |
| URL источника | Где получено изображение |
| Лицензия | Только фактически подтверждённая лицензия |
| URL лицензии | Страница с условиями лицензии |
| Citation | Полная библиографическая ссылка |
| `retrieved_at` | Время получения изображения |

Используйте кнопку выбора локального изображения: форма вычислит SHA256 и покажет preview.

Не используйте изображение только потому, что оно присутствует в машинной подсказке. Вручную
проверьте соответствие статье, точные байты и право использования. Запрещённые legacy image hashes
с `release_usable=false` форма отклонит.

Путь и SHA256 изображения должны быть уникальными. Путь должен быть Windows-safe и не должен
конфликтовать с путём другой группы.

### 3.6. Финальный экспорт source submission

1. Заполните все 150 групп.
2. Нажмите **«Проверить и экспортировать финальный JSON»**.
3. Нажимайте на ошибки в верхнем списке, чтобы перейти к соответствующей группе.
4. Исправьте все построчные и глобальные ошибки.
5. Повторно выберите lineage и identity JSON, если вкладка перезагружалась.
6. Получите `capacity_source_submission.json`.

Файл `capacity_source_submission_draft.json` является только резервным черновиком.

## Шаг 4. Передача результатов

В результате должны существовать три финальных файла:

```text
training_lineage_manifest.json
identity_resolution_submission.json
capacity_source_submission.json
```

Передайте владельцу downstream pipeline полные пути к этим трём файлам. Следующий этап должен:

1. Проверить schema, SHA256, queue fingerprint и перекрёстные привязки.
2. Проверить отсутствие training/evaluation leakage.
3. Проверить фактическую регенерацию плана после identity changes.
4. Собрать и провалидировать `machine_enrichment_v2.jsonl`.
5. Только после полной проверки создать `machine_assisted_draft.json`.

Эти три submission-файла ещё не являются решением кураторов и не означают готовность к
публикации.

## Частые ошибки

| Ошибка | Что делать |
| --- | --- |
| Введено `main` вместо revision | Найти точный 40-символьный commit SHA |
| SHA256 введён вручную с ошибкой | Выбрать точный локальный файл кнопкой формы |
| После перезагрузки source form потеряла bindings | Повторно выбрать два финальных JSON-файла |
| Выбрано `unresolved` | Найти проверенный canonical ID; это состояние блокирует финальный экспорт |
| Поставлен флажок регенерации без регенерации | Снять флажок и передать identity draft владельцу pipeline |
| Лицензия взята из машинной подсказки | Проверить лицензию по первичному источнику |
| URL содержит токен или `?query` | Использовать чистый стабильный URL без credentials и параметров |
| Финальный файл сохранён внутри `v5` | Переместить результат в отдельную рабочую папку, не изменяя workspace |
| Браузер добавил `(1)` к имени файла | Убедиться, какой файл является последним финальным экспортом |
